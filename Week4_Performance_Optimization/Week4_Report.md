# Performance Optimization Report — Inventory Analytics Tool

## 1. The Application

`baseline.py` is an inventory analytics tool: given a CSV of items
(name, category, quantity, price), it computes duplicate item names,
total value per category, the top 10 most valuable items, and writes a
text report. It's correct but was written as a "first draft," with
several common performance anti-patterns left in deliberately for this
exercise.

Test dataset: synthetic data generated by `generate_data.py`, seeded
for reproducibility, with a 15% duplicate-name rate and 60 categories
so every bottleneck actually shows up under profiling (not just in
theory).

## 2. Baseline Performance Analysis

Profiled with `cProfile` on a 30,000-row dataset:

```
$ python3 -m cProfile -s cumulative baseline.py large_inventory.csv baseline_report.txt
```

**`find_duplicates` alone accounts for 3.187s of the 3.376s total run —
94% of all execution time.** That's the clear primary target.
`compute_category_totals` (0.058s) is a distant second.

## 3. Bottlenecks Identified

### Bottleneck 1 — `find_duplicates`: O(n²) list membership checks

```python
# Before
seen = []
duplicates = []
for item in items:
    name = item["name"]
    if name in seen:                  # O(n) scan of a list
        if name not in duplicates:    # another O(n) scan
            duplicates.append(name)
    else:
        seen.append(name)
```

`in` on a `list` is a linear scan. Checking membership once per item,
for every item, makes the whole function O(n²) — on 30,000 rows,
potentially hundreds of millions of comparisons. This is exactly what
cProfile confirmed: 3.19 of 3.38 seconds.

**Fix:** replace the lists with `set`s. Set membership is an O(1)
average-case hash lookup, turning the function from O(n²) into O(n).

```python
# After
seen = set()
duplicates = set()
for item in items:
    name = item["name"]
    if name in seen:
        duplicates.add(name)
    else:
        seen.add(name)
return sorted(duplicates)
```

### Bottleneck 2 — `compute_category_totals`: O(C × n) redundant re-scans

```python
# Before
categories = set(item["category"] for item in items)
totals = {}
for category in categories:
    total = 0.0
    for item in items:                # re-scans ALL items, once per category
        if item["category"] == category:
            total += int(item["quantity"]) * float(item["price"])
    totals[category] = total
```

With 60 categories and 30,000 items, this scans the full item list 60
times over — 1.8 million comparisons to do what a single pass could.

**Fix:** one pass, accumulating into a `dict` (via `defaultdict`) keyed
by category.

```python
# After
totals = defaultdict(float)
for item in items:
    value = int(item["quantity"]) * float(item["price"])
    totals[item["category"]] += value
return dict(totals)
```

### Bottleneck 3 — `top_n_by_value`: full sort + redundant recomputation

```python
# Before
def value_of(item):
    return int(item["quantity"]) * float(item["price"])  # recomputed on every comparison

sorted_items = sorted(items, key=value_of, reverse=True)   # full O(n log n) sort
return [(item["name"], value_of(item)) for item in sorted_items[:n]]
```

Two issues: `value_of()` is recomputed by the sort on every comparison
Timsort makes (not once per item), and the entire list is sorted just
to keep the first 10 entries.

**Fix:** compute each value exactly once, then use `heapq.nlargest`,
which finds the top n directly rather than fully ordering everything.

```python
# After
valued = [
    (item["name"], int(item["quantity"]) * float(item["price"]))
    for item in items
]
return heapq.nlargest(n, valued, key=lambda pair: pair[1])
```

### Bottleneck 4 — `build_report`: string concatenation in a loop

```python
# Before
report = "..."
for name in duplicates:
    report += f"  - {name}\n"
```

Textbook version of this pattern is O(n²) in most languages, since
strings are immutable and each `+=` should, in principle, copy
everything built so far into a new string. The standard fix — building
a list and joining once — is still correct and applied here:

```python
# After
parts = ["..."]
for name in duplicates:
    parts.append(f"  - {name}\n")
return "".join(parts)
```

**Honest note on what profiling actually showed:** at 30,000 rows and
~3,800 duplicate lines, `build_report` cost **0.001s in both versions
— not a measurable bottleneck in this run.** CPython has an internal
optimization where `s += x` can resize a string in place when its
reference count is 1, making the "quadratic" pattern behave closer to
linear in practice under CPython specifically. The fix was kept anyway
because (a) it's guaranteed O(n) by the language semantics of
`str.join()`, not dependent on an implementation detail that doesn't
hold on other Python implementations (e.g. PyPy) or in cases with extra
references to the string, and (b) it's the standard, more readable
idiom. This is reported honestly rather than inventing a speedup number
that profiling didn't actually show.

## 4. Optimized Performance

```
$ python3 -m cProfile -s cumulative optimized.py large_inventory.csv optimized_report.txt

         244989 function calls (244977 primitive calls) in 0.111 seconds

   ncalls  tottime  percall  cumtime  percall filename:lineno(function)
        1    0.005    0.005    0.080    0.080 optimized.py:24(load_items)
        1    0.011    0.011    0.017    0.017 optimized.py:64(top_n_by_value)
        1    0.006    0.006    0.013    0.013 optimized.py:30(find_duplicates)
        1    0.011    0.011    0.011    0.011 optimized.py:50(compute_category_totals)
        1    0.001    0.001    0.001    0.001 optimized.py:82(build_report)
```

`find_duplicates` drops from 3.187s to 0.013s. `compute_category_totals`
drops from 0.058s to 0.011s. The single largest remaining cost is now
CSV parsing (`load_items`, 0.08s) — unavoidable I/O, not an algorithmic
inefficiency, and outside the scope of this optimization pass.

## 5. Before/After Benchmark (timeit, best-of-3, multiple dataset sizes)

Measured with `benchmark.py`, using `timeit.Timer(...).repeat()` and
taking the minimum of 3 runs per size to reduce system-noise:

| Rows | Baseline (s) | Optimized (s) | Speedup |
|-----:|-------------:|---------------:|--------:|
| 5,000 | 0.0974 | 0.0084 | 11.6x |
| 10,000 | 0.3566 | 0.0172 | 20.7x |
| 20,000 | 1.4414 | 0.0389 | 37.1x |
| 30,000 | 3.3185 | 0.0500 | 66.4x |

This table is itself evidence of the algorithmic difference: rows grew
6x (5,000 → 30,000), baseline time grew **~34x** (consistent with O(n²):
6² = 36), while optimized time grew **~6x** (consistent with O(n): linear
with rows). The speedup factor increasing with dataset size is the
signature of fixing quadratic behavior, not just a constant-factor
improvement — it will keep widening as the data grows further.

## 6. Correctness Verification

Before accepting any performance win, baseline and optimized outputs
were cross-checked on the same 30,000-row dataset:

```python
b_dupes = set(baseline.find_duplicates(items))
o_dupes = set(optimized.find_duplicates(items))
assert b_dupes == o_dupes                              # True, 3,808 names

b_totals = baseline.compute_category_totals(items)
o_totals = optimized.compute_category_totals(items)
assert set(b_totals) == set(o_totals)
assert all(abs(b_totals[k] - o_totals[k]) < 0.01 for k in b_totals)  # True

b_top = set((n, round(v, 2)) for n, v in baseline.top_n_by_value(items, n=10))
o_top = set((n, round(v, 2)) for n, v in optimized.top_n_by_value(items, n=10))
assert b_top == o_top                                   # True
```

All three checks passed. Duplicate names, category totals, and the
top-10 valuable items are identical between versions (compared as sets/
dicts rather than raw lists, since neither the original task nor either
implementation guarantees a specific tie-breaking order for duplicates
or top-N items with equal values — only that the *same set* of results
comes out).

## 7. Summary

| Bottleneck | Before (30k rows) | After (30k rows) | Complexity change |
|---|---:|---:|---|
| Duplicate detection | 3.187s | 0.013s | O(n²) → O(n) |
| Category totals | 0.058s | 0.011s | O(C·n) → O(n) |
| Top-10 selection | 0.025s | 0.017s | O(n log n) full sort → O(n log k) partial + no redundant recompute |
| Report string building | 0.001s | 0.001s | O(n²) in theory, not observed under CPython at this scale — fixed anyway for correctness across implementations |
| **Total run time** | **3.38s** | **0.06s** | **~57x** |

The single highest-leverage fix was `find_duplicates` (list → set),
responsible for the overwhelming majority of the total speedup. All
other fixes were still worth making — they're correct algorithmic
improvements with no behavior change — but this profiling process is a
good reminder to fix the bottleneck cProfile actually points to first,
rather than optimizing by intuition alone.
